## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
heaptide finds leaks in CPU, GPU (HIP and Mojo) and Python programs in one pass, without
rebuilding them. On an 8-thread malloc benchmark it runs 12x faster than heaptrack with 6.7x less
added memory. On every planted leak in its test suite, its direct/indirect split matches
LeakSanitizer's. It also sees HIP device and pinned host memory, Mojo's GPU buffers included,
which no other leak tool we know of covers on ROCm.

```
heaptide run [--gpu] [--py] [--py-depth N] [--every MS] [--snapshot-every S] [--out DIR] -- CMD...
heaptide snapshot DIR
heaptide report DIR [--json] [--top N] [--supp FILE] [--fail-on any|leaks|growth|none]
heaptide attach PID [--out DIR]  ·  heaptide detach DIR  ·  heaptide diff BASE NEW
```

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- Correction to v0.1.9: the "+10 MB per process" seen on GitHub runners was not heaptide's memory. The runner maps the first 8 MiB of any sparse `/dev/shm` file on first touch, with or without heaptide. On other machines a traced process costs about +1.1 MB, as before.
- The README shows CI, release, latest release, license and a live checks n/m badge.

## Changes

### Changed
- `rss_floor` does not count the shm table file's clean (read, never written) pages. Only those can come from the host instead of the shim.
- README badge row, and a `badges` branch that the cpu workflow writes `checks.json` to on main pushes.
### Removed
- `MADV_NOHUGEPAGE` on the shm mappings (added after v0.1.9, never released). The file never took huge pages, so it fixed nothing.

## Known limits

<!-- Honest list: slow paths, unsupported cases, flaky upstreams, anything UNVERIFIED. -->
- On a host like the GitHub runner, a traced process still shows about +8 MB of RSS from the shm file. It is clean and reclaimable, and every process that maps such a file pays it, not only heaptide.
- In the local VM with THP "always", a traced `sleep` showed about +2.8 MB over a bare one. Not investigated yet.
- Same platform limits as v0.1.9.
