## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
heaptide finds leaks in CPU, GPU (HIP and Mojo) and Python programs in one pass, without
rebuilding them. On an 8-thread malloc benchmark it runs 12x faster than heaptrack with 6.7x less
added memory. On every planted leak in its test suite, its direct/indirect split matches
LeakSanitizer's. It also sees HIP device and pinned host memory, Mojo's GPU buffers included,
which no other leak tool we know of covers on ROCm.

```
heaptide run [--gpu] [--py] [--py-depth N] [--every MS] [--snapshot-every S] [--out DIR] -- CMD...
heaptide snapshot DIR
heaptide report DIR [--json] [--top N] [--supp FILE] [--fail-on any|leaks|growth|none]
```

## Highlights

- **Who holds the memory:** under each PEAK row, the chain that keeps it alive:
  `held by: make_table c_cache.c:7 << global g_cache`. Reachable growth (caches, queues) gets an owner.
- **No restart needed:** `sudo heaptide attach PID` profiles a process that is already running.
- **A leak gate for CI:** `heaptide diff BASE NEW` lists NEW, GROWN, GONE and SHRUNK sites and exits 1
  on a new leak site.
- **VRAM over time:** `--gpu-timeline all|sites,streams,frag` draws each GPU site, each HIP stream and
  what the device holds beyond the live blocks.
- **One stack from Python to the GPU:** under `--py` (Python 3.12+) native and GPU sites end in the
  Python function that made them: `... <- py::load_weights train.py`. Mojo programs' own heap is
  visible too.

## Changes

### Added
- Retention paths: per site, the first holder that reached it (a site, a global's word, a thread,
  or memory from before attach); `held by:` under PEAK and `"held"` in `--json`.
- `heaptide attach PID [--out DIR]`: gdb loads heaptide into a running process; GOT slots of hooked
  functions are pointed at heaptide's; memory from before attach is a root.
- `heaptide diff BASE NEW [--fail-on new|grown|none] [--json] [--top N]`; `report --sites FILE` and
  `report --diff A B` underneath.
- `--gpu-timeline`: per-site VRAM over the run, split by HIP stream, and the device line (bytes in
  use beyond the live blocks, async pool reserved minus used); `"gpu_timeline"` in `--json`.
- Python frames in native stacks: `--py` adds `-X perf` on Python 3.12+; frames named from
  `/tmp/perf-<pid>.map`.
- Mojo's CPU heap: heaptide switches Mojo's bundled tcmalloc to libc at start
  (`KGEN_CompilerRT_SetAsanAllocators`), so Mojo blocks are tracked; no tcmalloc arena is mapped.
- `tools/ci-local.sh`: the CI workflow's steps in an Ubuntu 24.04 container, before a push.
### Changed
- Mojo and C++ frames print without their signature (`List::_realloc memory.mojo:454`).
- Unnamed frames carry their module offset; the file format adds the retention array (flag bit 2)
  and the timeline (flag bit 3). v0.1.3 files still report.
### Fixed
- A snapshot no longer ends a sleeping thread's `nanosleep`/`poll` early (a C `sleep(3)` ended after
  124 ms, a Mojo `sleep(5)` after 133 ms; the exit report then overwrote the snapshot).
- A HIP library loaded `RTLD_LOCAL` (ctypes) was not tracked.
- A static Python (Ubuntu) ended `--py` sites in the interpreter, before the Python frame.
- `attach` restores read-only RELRO after writing GOT slots.
- `diff` warns when frames are unnamed (no llvm-symbolizer), instead of listing every site as changed.

## Known limits

- `attach` sees only allocations after attach; a stale pointer in older memory can hide a newer
  leak (under-reports, never over-reports); Mojo's heap stays invisible when attached; needs
  ptrace rights (`sudo` under Yama 1).
- In a snapshot, a thread asleep in a system call is not signalled: its saved registers are not
  scanned, so a block held only there can show as leaked in that snapshot (never at exit).
- Holders are the first path found, recorded for memory live at the report.
- The GPU device line is device-wide: another process allocating on the same GPU shows up there.
- Python frames are function names only and need the report on the same machine (perf map).
- `diff` needs llvm-symbolizer; unnamed frames only match between identical binaries.
- Static ASan (clang's default) cannot be watched: a warning, no report.

## Upgrade / run

```
./build.sh
heaptide run --py -- python3 train.py           # Python frames in native/GPU sites
heaptide run --gpu-timeline all -- ./app         # VRAM per site over time
sudo heaptide attach PID                          # a running process
heaptide diff .work/base .work/new                # CI gate
```
Reports from v0.1.3 still read.
