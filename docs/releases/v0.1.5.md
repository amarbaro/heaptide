# heaptide v0.1.5

**Released:** 2026-10-12 · **Commit:** `116d704` · **Previous:** [v0.1.4](v0.1.4.md)

## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
heaptide finds leaks in CPU, GPU (HIP and Mojo) and Python programs in one pass, without
rebuilding them. On an 8-thread malloc benchmark it runs 12x faster than heaptrack with 6.7x less
added memory. On every planted leak in its test suite, its direct/indirect split matches
LeakSanitizer's. It also sees HIP device and pinned host memory, Mojo's GPU buffers included,
which no other leak tool we know of covers on ROCm.

```
heaptide run [--gpu] [--py] [--py-depth N] [--every MS] [--snapshot-every S] [--out DIR] -- CMD...
heaptide snapshot DIR
heaptide report DIR [--json] [--top N] [--supp FILE] [--fail-on any|leaks|growth|none]
heaptide attach PID [--out DIR]  ·  heaptide detach DIR  ·  heaptide diff BASE NEW
```

## Highlights

- **See every call path:** `heaptide flame DIR --open` writes one offline HTML page, an interactive
  memory flame graph (leaked, live, peak, allocated, temporaries; inverted view, search, zoom, Python
  and GPU frames in their own colors). `report --folded` feeds speedscope, flamegraph.pl or inferno.
- **Python mode about 10x faster:** `--py` now hooks CPython's own allocators, the way memray does,
  instead of running under `tracemalloc`. On 8M live objects: 30 s / 3.86 GB before, 2.9 s / 849 MB
  now (memray tracing every Python allocation: 2.8 s / 617 MB).
- **Stop without a restart:** `heaptide detach DIR` takes a last snapshot, unhooks the process and
  gives its tables back (1M tracked blocks: 98.5 MB resident attached, 59.8 MB after).
- **Attach is safe on programs with their own allocator** (Chromium's PartitionAlloc, jemalloc
  builds): a crash and a hang that hit Vivaldi are fixed.
- **Qt and QML apps read true:** the JavaScript heap no longer shows as 968 KB of false leaks, and
  JIT frames are named `[jit QtQml]`.

## Changes

### Added
- `heaptide flame DIR [-o OUT.html] [--open]` and `heaptide report DIR --folded METRIC`; the report's
  `--flame-data` is the page's input. `tools/flame-shot.sh` checks a page in headless Chromium.
- `heaptide detach DIR`: last snapshot, hooks pass through, GOT slots restored (RELRO stays
  read-only), signal handlers and sampler gone, tables released with `MADV_DONTNEED`. No report at exit.
- Python allocations through `PyMem_SetAllocator` (MEM and OBJ domains) and `PyTraceMalloc_Track`
  (numpy's array data); sites keyed by code object and instruction offset, merged by line.
- `tools/chromium-attach-repro.sh`: attach to a throwaway (or a given) Chromium browser, snapshot,
  watch its debugging port, capture threads and raw stacks on a hang.
### Changed
- The symbolizer is asked once per distinct address (on `bench/py_bench`: 1,597 requests instead
  of 22,088); report output is byte-identical on 14 test profiles.
- An attached report gives no GROWTH verdict: `GROWTH n/a`, JSON `"growth":"attached"` (live bytes
  count from 0 at attach, so the ramp read as FAIL on an idle plasmashell). File flag bit 4.
- `--py` no longer uses `tracemalloc`; the PYTHON section has the same format. GIL builds only.
- A skipped snapshot says how many threads were asleep and signalled.
### Fixed
- Attach forwarded to libc's `malloc` even when the program exports its own: a block from before
  attach reached libc's `free` (abort). It now forwards to what the dynamic linker bound.
- A thread's first stack capture inside the `mmap` hook could allocate through the program's own
  allocator while that thread held its lock: Vivaldi hung minutes after attach (libunwind's TLS
  block when attached, its `pthread_setspecific` key block in `run`).
- Attach after a detach reported success and hooked nothing; it now refuses.
- On a python with libpython in the executable (Debian, Ubuntu), extensions' own buffers (numpy's
  array data) reach their Python line: their `PyTraceMalloc_Track` GOT slots are pointed at heaptide's.
- Private writable memfd mappings (Qt's JavaScript heap, other JIT heaps) are scanned as roots.
- `sudo heaptide attach` left the output directory root-owned: no report could be written.
- `heaptide snapshot` returned before the report was written.
- `diff` lost `::` in names; non-ELF frames no longer reach llvm-symbolizer.
- The memfd root scan kept a 1 MiB static buffer resident in every program (+2 MB peak since the
  Qt fix) and searched the maps text quadratically: now mapped per report, searched per line.

## Known limits

- The Chromium hang fix is proven on a stand-in (`tests/c_ownlock.c`), not on a Chromium browser:
  a throwaway Vivaldi did not reproduce the hang, the user's did (2 of 3 runs before the fix).
- On Chromium only shared libraries' allocations are seen; its own C++ calls PartitionAlloc directly.
- After attach, a thread's `mmap`-family events have no stack until that thread has made a
  `malloc`-family call (the price of the hang fix).
- `--py` needs a GIL build; free-threaded Python gets no PYTHON section. It keeps a pointer table in
  process: +232 MB over memray on 8M live objects.
- Detach leaves the library mapped, inert; attaching again needs a restart.
- Earlier limits stand: attach under-reports (never over-reports), Mojo's heap is invisible when
  attached, a snapshot does not scan the registers of a thread asleep in a system call.

## Upgrade / run

```
./build.sh
sudo heaptide attach PID --out .work/ht          # a running process
heaptide snapshot .work/ht; heaptide detach .work/ht
heaptide run --py -- python3 train.py           # no tracemalloc any more
```
Reports from v0.1.4 still read.
